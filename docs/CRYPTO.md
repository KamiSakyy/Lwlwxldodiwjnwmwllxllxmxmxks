# Протокол MailGram: v1 (конверт) и v2 (двойной крысиный шаг)

Документ описывает ровно то, что реализовано в коде: `crypto/MailCrypto.java`, `crypto/Ratchet.java`,
`crypto/RatchetStore.java`, `crypto/Identity.java`, нативное ядро `app/src/main/cpp/`.

## 0. Общая картина

| Слой | Что делает | Где |
|---|---|---|
| Идентичность | пара ключей P-256, приватный ключ в Android Keystore (TEE, экспорт невозможен) | `Identity.java` |
| v1 «конверт» | статический общий секрет ECDH + HKDF + ChaCha20-Poly1305 | `MailCrypto.java` |
| v2 | рукопожатие X3DH + отдельный ключ на каждое письмо (выводится из SK и номеров `pn`/`n`) | `Ratchet.java`, `RatchetStore.java` |
| Примитивы | SHA-256, HMAC-SHA256, HKDF-SHA256, ChaCha20-Poly1305, CSPRNG, Curve P-256 | `app/src/main/cpp/mailgram_crypto.cpp` |
| Транспорт | письмо Gmail с темой `MailGram <8 hex id диалога>` | `net/GmailApi.java`, `sync/SyncEngine.java` |

Ключи **никогда** не покидают устройство. В коде нет ни секретов, ни приватных ключей: всё рождается
в Keystore при первом входе.

---

## 1. Идентичность

* Приватный ключ — P-256 (`ECDH`), генерируется в Android Keystore, привязан к устройству.
* Публичный ключ (raw, 65 байт) вкладывается в каждое исходящее письмо и в приглашение.
* Отпечаток безопасности = `SHA-256("MailGram/v1/safety" ‖ ключи, отсортированные по байтам)` →
  12 групп по 5 цифр (60 цифр). Показывается на экране «Сведения о чате» вместе с состоянием
  двойного шага и кнопкой отметки «проверено».

## 2. v1: первый контакт и совместимость

Пока для диалога не поднят сеанс двойного шага (собеседник ещё не прислал свой «шаговый» ключ),
сообщения идут в конверте v1:

```
общий ключ  = HKDF-SHA256( ECDH(мой приватный, публичный собеседника), salt = chatUid, info = "MailGram/v1" )
шифртекст   = ChaCha20-Poly1305(ключ, nonce, AAD = "MailGram/1|id|ts|from|to|chat", полезная нагрузка)
```

Полезная нагрузка — JSON: `t` (тип), `b` (текст или base64 медиа), `m` (MIME), `d` (длительность),
`n`/`s` (имя и размер файла), `r`/`rp` (ответ на сообщение), `w` (волна голосового), `pre` (предключ,
см. ниже), `fwd` (переслано).

## 3. v2: X3DH + отдельный ключ на каждое письмо

Реализация `crypto/Ratchet.java` повторяет **рукопожатие** X3DH из спецификации Signal, но
расписание ключей адаптировано под почту: состояние не «догоняет» другую сторону, а выводит ключ из
заголовка письма. Состояние сторон отсюда не зависит — рассинхронизация невозможна физически.

### 3.1. Начало сеанса (рукопожатие)

Сервера-хранилища предключей нет, поэтому предключ публикуется в приглашении (маркер
`X-MailGram-PreKey:`), в поле `pre` каждого письма и в поле `dh` (для ответчика — он же
«шаговый» ключ). В v2 `dh` и `pre` — один и тот же предключ отправителя (так письмо нельзя
«потерять» из-засохранённых сессий), а `EK` — эфемерная пара, которая участвует только
в DH2 рукопожатия:

```
инициатор:  DH1 = DH(мой постоянный,  постоянный собеседника)
            DH2 = DH(EK,              постоянный собеседника)
            DH3 = DH(EK,              предключ собеседника = его "dh")
ответчик:   DH1 = DH(мой постоянный,  постоянный собеседника)
            DH2 = DH(мой предключ,    постоянный собеседника)
            DH3 = DH(мой предключ,    «шаговый» ключ собеседника = его "dh")

S  = 16 случайных байт, переданы инициатором в поле "srt"
SK = HKDF-SHA256(DH1 ‖ DH2 ‖ DH3 ‖ S, salt = chatUid, info = "MailGram/DR/x3dh", 32)
```

ECDH коммутативен, поэтому все три DH у сторон совпадают байт в байт; отдельного обмена ключами
не нужно — сессия поднимается из заголовка первого же письма (`Ratchet.responder`).

### 3.2. Ключ сообщения

```
seedX = SHA-256("MailGram/seed/1" ‖ B64(публичный ключ идентичности X))     (публично выводимо)
CK(pn) = HKDF-SHA256(ikm = "turn:pn", salt = 0…0 ‖ seed_me ‖ seed_peer, info = "MailGram/DR/chain", 32)
MK(pn,n) = HKDF-SHA256(ikm = "msg:n", salt = CK(pn), info = "MailGram/DR/message", 32)
```

`pn` (оборот) и `n` (номер письма внутри оборота) считает **только отправитель**: `n` растёт на
каждое письмо, `pn` увеличивается на 1 после 1000 писем (или после смены сессии — тогда меняется
`S` и, соответственно, `SK`). Получатель берёт эти номера из заголовка и получает ровно тот же
`MK`: никакой локальный счётчик не может «отстать» или «убежать вперёд».

Письмо: `ChaCha20-Poly1305(MK, nonce, AAD, текст)`, где
`AAD = "MailGram/DR|2|id|ts|from|to|chat" ‖ B64(dh)|pn|n` — подмена любого поля (включая номера)
ломает тег, а не уводит сторону на чужой ключ.

### 3.3. Порядок доставки и повторы

* `pn` и `n` — счётчики отправителя; они же вход для вывода ключа, поэтому приём не «догоняет»
  отправителя и не может разойтись с ним: письмо читается по своим номерам из заголовка;
* очередь `SyncEngine` (`Prefs.retryQueue`) хранит письма, которые не удалось разобрать, и
  повторяет попытку на каждой синхронизации — письмо не теряется молча;
* анти-replay: последние `Ratchet.SEEN_WINDOW` (256) пар `pn:n` помнятся в файле сессии,
  повторная доставка того же письма отбивается с внятной ошибкой.

### 3.4. Почему без DH-шага на каждый ответ

Необратимый шаг ключа требует, чтобы обе стороны сделали его в один и тот же момент. В почте
момент нельзя согласовать: ответ может быть написан раньше, чем дойдёт исходное письмо, а письмо
может не дойти вовсе. Реализация «как в Signal» в 3.x ровно на этом и теряла входящие: тег не
сходился, и `SyncEngine` выбрасывал сообщение без следа. Поэтому расписание сделано выводимым
из данных письма — ценой отказа от forward secrecy (о чём честно сказано в приложении).

## 4. Служебные конверты

Внутри шифротекста ходят управляющие сообщения, которые не отображаются в ленте:

| `t` | Что делает | Поля |
|---|---|---|
| `react` | реакция на сообщение (снятие — `rm=true`) | `mid`, `e`, `rm` |
| `edit` | правка текста | `mid` |
| `del` | удаление у обоих | `mid` |
| `pin` | закрепление и открепление | `mid`, `v` |

## 5. Письмо

```
Тема:   MailGram <8 hex>
Тело:   base64(JSON конверта)     ← единственное, что видно в почте
Адреса: отправитель → получатель  ← метаданные видны всегда (сервера нет)
```

## 6. Что защищено, а что нет

**Защищено.** Содержимое сообщений и вложений; подмена любых полей конверта (AAD); повторная доставка
(удаление использованного ключа); подмена открытого ключа видна через номер безопасности; компрометация
одного сообщения не раскрывает остальные.

**Не защищено.** Метаданные (кто, кому, когда, размер); собеседник, чьё устройство уже взломано;
отсутствие внешнего аудита кода; режим Testing в Google Cloud (refresh-токен живёт 7 дней).

## 7. Проверка

* Проверка расписания: `Ratchet.messageKey()` — чистая функция от `SK`, seed'ов сторон и
  `pn:n`; симметричность проверяется на сборке и на самотесте приложения (HKDF/ChaCha-векторы
  RFC 8439/5869/4231, FIPS 180-4).
* Самотест в приложении: «Настройки → Безопасность» прогоняет тест-векторы RFC 8439 / 5869 / 4231 / FIPS 180-4.
* Номер безопасности в карточке чата — 60 цифр из `NativeCrypto.safetyNumber`.

## 8. Реализация примитивов

`app/src/main/cpp/mailgram_crypto.cpp` — SHA-256, HMAC-SHA256, HKDF-SHA256, ChaCha20-Poly1305, CSPRNG
(`getrandom`/`/dev/urandom`), самотест на тест-векторах. Сборка — NDK 28, C++17, `-O2`, без внешних
зависимостей (никаких OpenSSL/BoringSSL: код собран и проверен в этом репозитории).
